# 镜维度 · 机制详解

本文写给**想看懂它是怎么做的**的人：每一套机制的实现层次、关键参数、以及排查入口。
面向玩法的简介见仓库首页 [README.md](../README.md)。

---

## 0. 三层结构：谁负责什么

镜维度不是一个"塞满内容"的模组，它的实现刻意分成三层，**每层只做一件必须由它做的事**：

| 层 | 由谁实现 | 负责 |
|---|---|---|
| **世界** | `kubejs/data/mirror/**`（数据包，KubeJS 加载） | 维度、维度类型、生物群系、噪声设置、玻璃层特征 |
| **物理** | 本模组的 Java 代码（+ Pondus） | 重力方向、速度与位置补丁、下落方块着陆补丁、传送门方块与遮罩、掉落物生成、JEI |
| **规则** | `kubejs/server_scripts/mirror_n*.js`（11 个模块） | 加工配方的注册/计数/替换、交界处防抖、镜外模式、指令 |

设计原则只有两条，但整个项目都靠它们撑着：

1. **配置是唯一真相**：所有可调参数集中在 `kubejs/startup_scripts/mirror_config.js`（约 1000 行）。
   模组只提供"原语"（读写重力方向、判断方块、生成掉落物……），脚本通过 `MG_API` 调用它们。
2. **物理只有一处实现**：掉落物与下落方块的物理**全部在服务端模组里算**，
   脚本侧只做规则判定。两边都改速度会产生"各算一次"的抖动。

## 1. 世界：镜维度是怎么搭出来的

### 1.1 数据包内容（`kubejs/data/mirror/`）

```
dimension/mirror.json              维度定义（引下面两个）
dimension_type/mirror.json         维度类型（高度、坐标比例、天空/雾/水色…）
worldgen/biome/mirror.json         生物群系（冷色调、不下雨）
worldgen/noise_settings/mirror_void.json   虚空地形
worldgen/configured_feature/*.json 8 个玻璃层特征（白玻璃 ×4 + 黑玻璃 ×4）
worldgen/placed_feature/*.json     把上面 8 个特征摆到指定 y
```

### 1.2 几何

| 概念 | 值 | 说明 |
|---|---|---|
| 世界高度 | −192 ~ 191 | 384 格，够装下"镜内 + 镜外" |
| **镜内** | −64 ~ 63 | 玩家正常活动区 |
| **分界（镜面）** | y = 0 | 脚本判定的参考线取 **y = −1**（下落方块的参考线比玩家低一格，见 §2.4） |
| 镜外 | 其余部分 | 掉出去会被切成冒险/旁观 |
| 白玻璃层 | y = 62/63、−64/−65 | 镜外的可视边界 |
| **黑玻璃层** | y = 0/1、−1/−2 | 上下界面；玩家可以自己在这里挖洞/铺平台 |

玻璃层由 `worldgen` 特征生成（**只填空气、不覆盖玩家放下的方块**），
所以你在镜维度里搭的东西不会被世界生成"吃掉"。

### 1.3 与主世界的坐标关系

- **X/Z**：走原版机制 —— 维度类型里的 `coordinate_scale: 16`，
  于是主世界 1 格 = 镜维度 1/16 格（便于用同一套坐标找回来）。
- **Y**：本模组**线性重映射** —— 主世界 −64~319 压进镜维度 −64~63：

```
主世界  -64 ─────────── 319      (384 格)
          │  线性映射  │
镜维度  -64 ───────────  63      (128 格)
```

两端对齐、单调，所以来回自洽：主世界地面 y≈70 进镜维度约在 y≈−20，稳在镜内。

### 1.4 一个坑（写数据包时踩过）

`noise_settings` 里两个字段的类型必须严格照抄原版（`sea_level` 是整数、
`disable_mob_generation` 是布尔），写成浮点会让**整个维度加载失败**
而且报错信息指向别处。这类 JSON 建议用生成器产出，不要手抄。

## 2. 物理：重力反转是怎么实现的

### 2.1 为什么必须用模组

原版有一整套"世界只能朝下"的硬编码：流体、寻路、AI、碰撞、掉落物寿命……
没法靠数据包或脚本改。所以"每个实体一个重力方向"这件事交给 **Pondus**，
本模组负责把它**修到能用**、并补上它没覆盖的部分。

### 2.2 Pondus 的三个缺陷（本模组的补丁点）

| 缺陷 | 现象 | 本模组的处理 |
|---|---|---|
| 服务端换向瞬间算错"换向前速度"，把速度整体清零 | 掉落物一过界就**垂直掉下来**、水平动量丢失 | 在换向前保存速度、换向后按新方向还原 |
| 白名单只覆盖生物 | 掉落物 / 下落的方块在镜维度**完全不反向重力** | 模组侧接管这两类实体 |
| 换向时给实体位置加一次平移 | 视觉上"过界处瞬移一小段" | 一个 mixin 把这次平移抵消掉 |

> 那个 mixin 注入的是 **Pondus 的类**，所以它的配置是 `required:false` +
> `injectors.defaultRequire=0`：目标缺失或注入点找不到时**只跳过**，不影响启动。

### 2.3 交界处防抖（否则会在线上疯狂翻转）

分界线附近是"抖动的重灾区"：实体停在 y≈0 时，每 tick 都在两个半区之间反复，
重力方向跟着来回翻，视觉上就是"抽搐"。三道闸门：

| 参数 | 作用 |
|---|---|
| `falling_hysteresis` / 玩家与生物的 `dead_zone` | **迟滞带**：要离开分界线一定距离才允许换向 |
| `player_flip_gap` / `entity_flip_gap` / `falling_flip_gap` | **冷却**：换向后这么多 tick 内不再换 |
| 稳定的方向读写通道 | 方向写在实体数据里（`DirectionWriter`），服务端与客户端读同一份值，避免两边各算一次 |

### 2.4 下落方块的两个特殊处理

**① 参考线下移一格。** 下落方块的碰撞箱高度是 0.98、且它的 y 是**底面**而不是中心，
用玩家的参考线会让它永远差一点过不去。所以下落方块用 `fallingSplit = −1.0`。

**② 着陆补丁。** 反重力下实体"朝上飞"，原版 `onGround()` 永远为 false，
于是方块永远放不回世界、最后变成掉落物。模组自己判定：

```
连续 N tick 几乎静止（静止阈值）
  → 检查运动方向前方那一格是否有碰撞
    → 有：把方块放回世界（变回方块），实体消失
    → 无：前方是空的，只是暂时停住，继续飞
```

补丁只在**反重力这一侧**生效；正常下落（上侧）一律交给原版，
这样上侧的观感与"没装本模组"完全一致。

## 3. 规则：重力方块加工是怎么判定的

实现在 `kubejs/server_scripts/mirror_n3_recipes.js`（约 1500 行），
配置在 `mirror_config.js → gravityBlockRecipes.list`（46 条）。

### 3.1 配方的形状

```js
{
  id: 'gravel_to_iron_block',
  input: 'minecraft:gravel',        // 什么方块在下落
  output: 'minecraft:iron_block',   // 变成什么
  crossings: 2,                     // 需要几次重力切换
  trigger: 'crossing',              // crossing = 于交界处；landing = 落在某方块上
  // landing 才需要：
  on: '#c:storage_blocks',          // 落点（可写一条、一组、或标签）
  map: { ... },                     // output 写 '@mapped' 时：落点 → 产物 的对照表
  drop: true,                       // 产物以掉落物弹出（而不是原地放成方块）
  insert: { items: [...], count: 1, force: true },   // 落在容器上时往里塞东西
  hint: '一句给玩家看的前提提示',
}
```

三种动态产物：

| 写法 | 含义 |
|---|---|
| `'@landed'` | 变成**落点那一块**（铁砧落在矿物块上 → 变成那一块） |
| `'@mapped'` | 按 `map` 表把落点翻成产物（脚手架落在哪种树叶上 → 对应树苗） |
| 普通 ID | 固定产物 |

### 3.2 次数怎么数

**数的是"重力方向切换次数"**，不是"穿过某条线"：

- 早先的写法是"跨过参考线"，但模组的迟滞带一调、换向点就移动，
  而那条线是写死的 —— 于是"视觉上来回好几次、计数只涨 1"。
- 现在直接读实体当前的方向，与上次不同就 +1。视觉与程序天然统一，
  而且对所有实体通用（掉落物 / 玩家 / 生物同一套）。

**计数身份 = 实体 id，一个实体一份状态。**
这一点被反复验证过：任何"按位置/按名字合并状态"的做法都会出问题 ——
同一竖列的多个下落方块会共用计数，**连"上一次方向"也会共用**，
于是脚本每处理一个就与另一个留下的方向不同、**每 tick 记一次假翻转**，
一秒就能把次数推到上限（真实事故：10 个脚手架在 1 秒内全变成蜘蛛网）。

> 推论（写这类系统时的通用判据）：把状态按位置合并之前，先检查里面有没有
> "只对单个实体才有意义"的字段（方向、速度、上一次高度、UUID…）。有，就不能合并。

### 3.3 落点判定的几何（这里踩过两个坑）

判定用的是**探针**：在实体所在的那一竖列上，逐个格子读方块状态，与 `on` 比对。

1. **探的是"碰撞箱实际占的格子"，不是"脚下那一格"。**
   因为 `entity.getY()` 是碰撞箱**底面**而不是格子中心：
   向上贴天花板时，若按 `y+1` 去探，只有当实体完全贴住的那 0.02 格才判得到，
   从下方靠近的整段都会漏掉 —— 现象是"看着明明贴上了，配方却一次都不触发"。
   现在的窗口是 `floor(box.minY) … floor(box.maxY − ε)` 再加上下各一格。
2. **高速下落要预判。** 原生重力下下落方块最快约 2 格/tick，
   可能一帧之内从"还差两格"直接变成"已落地并被原版放回方块"，中间那一瞬**没有任何一帧采到过**。
   所以在**速度超过 0.5 格/tick** 时，额外往运动方向多看 1 格（`landing_lookahead: 1`）。
   这个开关刻意**按速度生效**：低速靠近时不预判，避免"隔空取物"。

### 3.4 落点必须摆在下落实体那一竖列

下落实体**只在竖直方向动**，X/Z 一格都不会挪。所以：

- 落点摆在实体那一列 → 一定会碰到；
- 摆在隔壁一列 → **永远碰不到**，而现象与"配方坏了"完全一样。

因此 `/mirror recipes` 会直接念出坐标：

```
· minecraft:scaffolding  处理 249 tick，最高切换 8 次
      落点该摆在哪: x=-35, z=4，y=-4 ~ 18（就是这一竖列；铺满整个水平面一层最省事）
      旁边出现过: minecraft:flowering_azalea_leaves
```

没命中时，日志还会替你把话说完：

```
[镜维度·配方] ↑ 它这一列 x=-35 z=4（y=-6 ~ 18）实际有: y=-4=minecraft:flowering_azalea_leaves
[镜维度·配方] ↑ …★ 你要的「minecraft:soul_sand」就在隔壁：(-35,-4,3)=… （差 z 1 格）—— 挪进 x=-35 z=4 这一列即可
```

**最省事的做法：把落点方块铺满整个水平面的一层。** 谁掉在哪一列都碰得到。

### 3.5 落点的"结实程度"为什么会改变结果

以脚手架为例（原版 `ScaffoldingBlock`）：

- 脚手架**方块**只在下方 6 格内**没有结实支撑**时才活下来（否则变成稳定方块、这次下落结束）；
- 落在**满格**方块（泥土 / 灵魂土 / 下界岩 / 荧石）上 → 当场变成稳定方块，加工终止；
- 落在**支撑形状不满格**的方块（灵魂沙 / 泥巴 / 树叶）上 → 立刻又变回下落实体，继续往复。

所以给脚手架选落点时，"不结实"不是缺点，而是**能反复接触的前提**。

### 3.6 触发优先级：landing 先于 crossing

`landing` 的条件更具体（除了次数还要求贴着某个方块），`crossing` 只要求次数。
同一次数下两者都可能满足时**让更具体的赢** —— 否则"4 次 + 落在树叶上 → 树苗"永远会被
"4 次 → 别的产物"抢先。引擎会把同一次数下的所有 `landing` 候选**逐个试一遍**
（落点不同，必须现场查方块才知道），这一点踩过：早先只试第一条，
于是"第二种落点完全没反应"，且没有任何报错。

### 3.7 容器与掉落物

- **落在容器上塞物品**：先问模组"这个容器装得下吗"（`canInsertIntoContainer`），
  装不下就不触发、让方块继续往复；`force: true` 表示"满罐也触发"。
  随机物品是在**判定时**就抽定的 —— 否则会出现"方块变了、物品却没进去"。
- **`drop: true`**：产物调模组的 `dropItem` 生成**物品实体**，**绝不** `setBlockAndUpdate`。
  树苗这类东西原地放成方块会把落点盖掉，玩家也捡不走。
  掉落物的初速度刻意很小（横向 0.06、向上 0.04）—— 弹出发生在分界线附近，
  用原版"方块被破坏"那种 0.2 的抛射速度会被反向重力瞬间甩飞，观感像"炸出来"。

## 4. 传送门

### 4.1 结构（3×3×3）

```
底层  抛光黑石        中层  8 格空气 + 中心 1 格玻璃        顶层  平滑石英
```

- 点燃物品：**望远镜**（右键中心玻璃）；
- 玻璃取 `c:glass_blocks` 标签 —— 任意模组的玻璃都能用；
- 传送门方块与传送逻辑都是本模组自己的（不依赖 PortalJS）。

### 4.2 到达侧行为

- 从主世界过去时，**落点自动建门**并点燃，避免"过去之后回不来"；
- 回程**不靠坐标反算，而是找最近的门**；
- 站在门里时客户端有一层渐现遮罩（`MirrorPortalOverlay`），避免瞬间切换的突兀感。

## 5. 镜外模式

镜维度在 −64 ~ 63 之外是镜外。掉出去会：

- 切成**冒险 / 旁观**（随机二选一，配置里可改），进入与离开都有提示；
- 不掉血、不死亡 —— 它是"流放区"，不是死亡区。

## 6. 配置速查

全部集中在 `kubejs/startup_scripts/mirror_config.js`。常改的几项：

| 项 | 位置 | 说明 |
|---|---|---|
| `gravity.enabled` | `gravity` | 重力反转总开关 |
| `gravity.*_dead_zone` / `*_flip_gap` | `gravity` | 交界处防抖（迟滞带 / 冷却） |
| `gravity.count_mode` | `gravity` | 计数方式（`flip` 读方向，推荐） |
| `gravity.landing_lookahead` | `gravity` | 高速下落的落点预判格数（0/1/2） |
| `gravityBlockRecipes.list` | `gravityBlockRecipes` | 46 条加工配方 |
| `mirrorPortal.*` | `mirrorPortal` | 门的结构方块、点燃物品、Y 映射范围 |
| `outerRegion.*` | `outerRegion` | 镜外的游戏模式与提示 |
| `layout.*` | `layout` | 高度、镜内范围、分界线、玻璃层 |

改完**服务端脚本**在游戏里 `/reload` 即可；改 **startup 脚本**（含配置）需要重启游戏
或 `/kubejs reload startup_scripts`；改**维度类型**必须退出世界再进。

## 7. 排错入口

| 症状 | 先看 |
|---|---|
| 重力没反转 | `/mirror info`、`/mirror gravity`（总开关 / 参数），再看是否装了 Pondus |
| 配方不生效 | `/mirror recipes <方块关键词>` —— 看"活动范围""最近 3 秒""**落点该摆在哪**""旁边出现过" |
| 方块压根没掉 | 它的原版前提（例如脚手架下方 6 格内不能有结实支撑）；`/mirror recipes` 里那条 hint 写了 |
| 掉出去被切模式 | 这是镜外（设定），`/mirror back` 回来 |
| 门点不着 | 结构必须是 3×3×3 的三层，中心那格是玻璃，点燃物品是**望远镜** |

日志里所有与本模组相关的行都带 `[镜维度·…]` 前缀，直接搜这个前缀比翻整份日志快。
